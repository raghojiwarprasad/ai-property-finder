# Build sequence for Claude or Cursor

## Before coding

Read PRODUCT_DECISIONS, the vision, the end-to-end experience and screen contracts. Treat the earlier ZIP as optional reference. Inventory its reusable behaviour and liabilities, but do not preserve its interface simply because it exists. Do not implement career trajectory or import Cooper data.

Create an implementation status file with requirement IDs, current stage, checks completed and remaining blockers. The status file is a factual record; it must distinguish implemented, fixture-only, provider-unverified, content-planned and production-ready.

## Stage 1: design and interaction contract

Design arrival, CV input, goal, first lesson, feedback, Today, My path and My work. Use realistic fictional content from the supplied use cases and golden lessons. Include error and mobile states. Demonstrate a full first session with a personal explanation, a task and an appropriate response to a wrong answer. Do not build a large marketing site first.

Exit: the primary action is clear on every screen; goals change depth; examples are grounded; planned content looks planned. The user can review a concrete flow before substantial backend work.

## Stage 2: persistent learning slice

Implement identity, guest sessions, draft persistence, manual experience, goal interpretation using reviewed mappings, one complete lesson and deterministic assessment. Save attempt and evidence versions. Implement Today with the actual next action. Use fixtures only in an explicitly labelled development mode.

Exit: a learner can start, submit, receive accurate feedback, refresh and continue without losing work. Two users cannot access each other's records. No UI-only completion state substitutes for persisted evidence.

## Stage 3: CV and contextual AI

Add bounded document parsing, source-backed facts, correction, runtime personal examples and contextual tutoring. Connect an actual model provider through the gateway after reviewing current SDK documentation. Test invalid output, timeout and prompt injection. Personalisation failure offers honest recovery.

Exit: the first lesson uses supported experience, a learner can correct it, and a real provider session passes the same flow as deterministic development fixtures. No provider secret reaches the browser.

## Stage 4: adaptive evidence loop

Implement distinct item families, assistance history, criterion-based written feedback, transfer, review scheduling, appeals and versioned next-step rules. Add the four short outcome bundles and research starter only when their full evidence paths are reviewed.

Exit: a correct, incorrect, assisted and ambiguous answer produce appropriately different next steps; CV background never grants capability; changing goals preserves compatible evidence.

## Stage 5: work and constrained practice

Build artefact versioning, comparison, export and deterministic simulations. Connect simulation failures to concept repair. Add code execution only after the separate isolation gate; it is not required to demonstrate the first product.

Exit: useful work is saved, feedback is actionable, assisted work is labelled and simulations cannot perform real external actions.

## Stage 6: pilot hardening

Implement profile controls, retention/deletion jobs, accessibility verification, mobile polish, live-provider failure handling, cost reporting, content operations and a support route. Complete release gates in 09_MEASUREMENT_AND_LAUNCH.

Exit: real people can use the product without coaching, no severe factual or grading issue remains unresolved, and operations can recover a failed evaluation without losing work.

## Stage 7: growth and commercial experiments

Only after the core loop is useful, implement sanitised challenge sharing and measure downstream learning. Consider billing after observing value, retention and actual cost. Do not add career trajectory, job matching or social networking during these stages.

## Team responsibilities

One accountable product/design owner, one full-stack implementation owner and one curriculum/assessment owner are the minimum responsibility areas. One person can cover multiple areas in a prototype. Technical content and research tasks need qualified review; coding assistants do not remove that requirement. Security and accessibility review should occur before external access, with specialist help where necessary.

## How to use coding assistants effectively

Use the master prompt, then one stage prompt at a time. Ask the tool to read the relevant PRDs, cite requirement IDs in its plan and demonstrate working behaviour. Request a brief report of what changed, what was tested, which provider paths were actually exercised and what remains incomplete. Avoid one enormous “build everything” instruction that rewards plausible screens over learning quality.

No calendar estimate is fixed here because the team, stack, available content and quality of reused code are unknown. Scope by completed gates rather than a promise that an AI agent can finish a production learning platform in a weekend.
